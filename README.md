# Scriptorium

A git-backed operating system for a research operation: two task queues (one for
Omri, one for scriber agents), a typed dependency graph, an append-only
hash-chained event log, and a Merkle state root that makes the whole thing
verifiable at any commit. The design spec is the published "Scriptorium"
artifact; `docs/hashing.md` is the verification scheme.

## Install

```sh
uv sync                     # creates .venv with the `scr` command (Python ≥3.10, PyYAML); or: pip install -e .
.venv\Scripts\scr.exe up    # migrate to journal mode, start the UI + watcher, register both at logon
```

## Journal mode (nobody runs git here)

The scriptorium repo commits itself. Every state-changing `scr` command (task set, event, answer,
chore run, …) ends by refreshing the derived views and committing whatever is dirty, with the actor
and the command in the message (`[steward:T-0025] task set T-0025 returned ...`); the watcher commits
what scribers write to log.md/report.md every tick. `git log` is the audit trail, `scr history`
reads the snapshot chain out of it. Concurrent callers are serialised by `.scr/journal.lock`; a
crashed git's empty `*.lock` file is removed automatically after a minute. There is no pre-commit
hook any more (verification happens before writes, not at commit time), and no reason to type `git`
in this folder — if you do, the next `scr` call simply journals on top of it.

## Layout

```
config/      weights.yaml limits.yaml workloads.yaml     — Omri edits; Observer proposes
tasks/<id>-<slug>/  task.yaml spec.md log.md report.md review.md
events/events.jsonl   append-only, hash-chained; the log the records are a cache of
graph/graph.json      regenerated view of all edge sets + hashes
state/STATE.json      the snapshot: state root, Merkle root of tasks, graph root, chain head
queues/scribers.md    ranked view (regenerated)     queues/omri.md  decision briefs + ## Inbox
reports/daily weekly  Observer output
```

The code's own files ship inside the package, not the state root: `scr/assets/` holds `templates/`,
`ui/`, `agents/*.md` (standing instructions for Intake, Prioritizer, Steward, Concierge, Observer) and
`hooks/`. `scr assets [templates|ui|agents|hooks]` prints where the installed copy is. The live chore list
stays state: `<root>/ui/chores.yaml` wins over the shipped empty one.

Truth lives in `tasks/*/task.yaml` and `events/events.jsonl`. Everything else is
derived and regenerated by `scr refresh`, which every mutating command runs.

## Daily use

```sh
scr verify                                  # always first; exit 1 = the tree is not trustworthy
scr score                                   # ranked ready tasks with their graph terms
scr dispatch --dry-run                      # conflict-free set that would run next
scr --actor prioritizer dispatch            # mark them dispatched (attempts += 1)
scr --actor steward:T-0006 task set T-0006 in_progress
scr --actor steward:T-0006 task set T-0006 submitted
scr --actor steward:T-0006 task set T-0006 accepted
scr --actor steward:T-0006 task set T-0006 merged --tokens 1800000
scr graph analyze                           # hubs, chains, orphans, unlock yield, conflicts, depths
scr graph impact T-0003 --decls controlled_query   # blast radius of a statement change
scr graph context T-0006                    # what a Steward packs for the Scriber (informs edges)
scr edge add informs T-0005 T-0006 --weight 0.8 --reason "same reduction, different oracle"
scr history                                 # snapshot chain across commits
scr diff-state HEAD~3                       # what changed, by hash, since then
scr checkin open / close                    # Omri's minutes
```

Every `scr` call takes `--actor`; use it. The log is only as informative as the
actors are honest about who they are.

## Running a batch (the automated path)

```sh
scr verify && scr --actor prioritizer dispatch --allow-statements   # pick the conflict-free set (cap: limits.yaml concurrency)
scr launch [--mode tabs]        # worktrees (scr spawn) + brief + in_progress + one Claude session per task
scr watch --once                # one Steward tick: checkpoint commits, scope drift, HELP: lines, submissions
```

`scr task brief <id>` renders the launch prompt from the record (spec.md is the brief — never
hand-write prompts). `scr launch` runs sessions detached (`claude -p`); `--mode tabs` opens a Windows
Terminal tab per task so you can watch. `scr watch` is the mechanical half of the Steward for every
running task at once; every tick it also commits each running worktree on its task branch
(`[checkpoint]`), so nothing ever exists only in a worktree. `--auto-review` has a headless Steward
session fill review.md on each submission (the decision stays yours unless `--auto-decide`);
`--unattended` turns everything on. Landing is `scr land <id> --merge`; mission worktrees with
uncommitted work are swept by `scr sweep --merge`; finished worktrees are retired (quarantined,
never deleted) by `scr retire <name> --execute`. Phase C of a Lean task can go through loopy:
`<scr assets hooks>\loopy_phase_c.ps1 -Root <root>`. The old PowerShell hooks are under `scr/assets/hooks/retired/`.

## Unattended operation (the normal mode)

```
scr up                # (or: powershell -ExecutionPolicy Bypass -File <scr assets hooks>\scriptorium_up.ps1 -Root <root>)
scr up --restart      # after an update; the UI also restarts itself when its code changes
```

starts the UI at http://127.0.0.1:8765/ (your entry point: what needs you, every task's record and
history, a Discuss button on every card that opens a Claude Code session running as the ticket's role
(`claude --agent scriptorium-<role>`; the agent files are written to `~/.claude/agents/`). The session
introduces itself in two lines and waits for you; its brief is an index of the ticket, and it reads the
records your request needs, then carries out what you decide with scr. System alarms show as one card
per task and kind (`events:<task>:<kind>:<ts>`; Dismiss acks the whole group)) and the watcher in
`--unattended` mode, and registers
both at logon. Updates: `scr update <bundle.zip|folder>` copies the files in and migrates. Unattended = every mechanical decision is taken by the system:
submissions are reviewed by a headless Steward (`--auto-review`), accepted when the checks are
mechanical and the statement diff is empty (`--auto-decide`), landed as PRs and merged into the
agents' `main_branch` (`--auto-land`), Inbox lines and report `unlocks` become tasks (`--auto-intake`),
and the queue is refilled up to `concurrency` (`--auto-dispatch`). What still reaches you, in the UI:
the five gates — new/changed statements, direction decisions, stuck tasks, config changes, seeding.

You do not have to keep the page open to learn that something needs you. Every card the page shows is
also pushed out of band by the watcher tick that first sees it — a Windows toast (PowerShell + WinRT, no
module) and, if you turn it on, an SMTP email — once per card key; Dismiss (`scr ack <key>`) silences it for
good. Channels, host, port, addresses and the NAME of the environment variable that holds the SMTP password
live in `config/notify.yaml` (never the password itself). `scr notify --test` sends one test message per
enabled channel and prints the result; `scr notify` lists the standing cards and which were pushed. A failed
push is a `notify FAILED:` line in `reports/steward_watch.log`. The page title reads `(N) Scriptorium` while
N cards stand, so a pinned tab shows the count (T-0090).

Permission mode: every Claude session the operation starts — the headless ones (`claude -p`: scribers,
Steward reviews and tooling reviews, the nightly Intake, the Concierge) and the interactive ones you open
with Discuss — runs in Claude Code **auto mode** (`--permission-mode auto`), and a session started in a
worktree gets `--add-dir <scriptorium root>` so it can read its `tasks/<id>/` record; every session also gets
`--add-dir <the package's assets/>` for `agents/*.md` and `templates/`.
The reason is that a headless session has nobody to approve a prompt: under `acceptEdits` every
`scr.exe`, venv `python.exe` and `lake` call and every read outside the worktree was denied, so three
reviews in a row wrote a Decision they could not apply and the nightly Intake created nothing (T-0077).
In exchange the briefs forbid what the mode would otherwise allow: never merge a branch, never edit a
Lean statement, never run git in the scriptorium root (it journals itself). The default lives once, in
`scr/run.py` (`DEFAULT_PERMISSION_MODE`); `scr config set limits claude_permission_mode <mode>` overrides
it for every session, and `scr launch --permission-mode` / `scr watch --permission-mode` for one run.

Branch policy: `main_branch` (master) is the agents' branch and the full history log; the
`trusted_branch` (trusted) holds sources of truth and only you push to it (protect it on GitHub:
require a PR + your review, restrict who can push). `scr sweep --merge` commits and
lands any uncommitted mission work so nothing exists only in a worktree.

## Fixing Scriptorium itself (hotfix)

Tooling breaks sometimes and the fix has to land in the live checkout, not in a worktree. That is a
**hotfix**, and it is a task like any other: *Fix a bug…* in the UI (or `scr hotfix open "<symptom>"`,
or just editing — the journal opens a hotfix the moment a tooling path is committed with none open)
creates the record and a Toolsmith session; every journal commit while it is open is appended to the
record; `scr hotfix close --summary ... [--unlock "title | why"]` runs the tests, writes the report and
submits it; the watcher's Steward reviews the diff and proposes follow-ups, which Intake turns into
tasks; accepted → merged. An external agent without a shell here (Claude in Cowork) uses two files:
`.scr/hotfix/pending.json` before editing and `.scr/hotfix/close.json` when done. See `agents/toolsmith.md`.

## Freezing a workload

`frozen: true` on a workload's entry in `config/workloads.yaml` (T-0272; absent means `false`) stops the
automation for that workload's tasks and nothing else: the watcher does not auto-dispatch, auto-review or
auto-land them (it logs one `frozen: N <workload> tasks held` line per tick), and Intake files new proposals
for it as `triaged` with the note "frozen workload: parked for the thaw" instead of `ready`. Tasks already
running finish their session and are submitted as usual; they then wait for the thaw. `scr verify` prints
one `info` line per frozen workload and the UI header shows "<workload> frozen". Other workloads are untouched.

The exception path, for a hotfix during a freeze, is your explicit dispatch: `scr --actor omri dispatch <id>`
(then `scr launch`). Any other actor, and a bare `scr dispatch`, is refused or skips the task.

To thaw: set `frozen: false` (or delete the key); the next watcher tick dispatches, reviews and lands as
before. Intake's parked `triaged` tasks need no promotion: `scr dispatch` already picks an unblocked
`triaged` task, so they are dispatchable again from that tick on.

## Lifecycle

`proposed → triaged → (blocked) → ready → dispatched → in_progress ⇄ checkpoint →
submitted → accepted → merged → closed`, with `returned` (back to ready,
attempts counted at dispatch) and `escalated → omri_queue` (Gates 1–3). Illegal
transitions are refused unless `--force`, which is itself logged. A task that
reaches `merged`/`rejected` automatically flips its dependents to `ready` when
nothing else blocks them, and a rejected blocker raises a `blocker_rejected`
system event for Gate 2.

## Graph

Vertices are tasks (milestones are `kind: milestone`). Stored edges:
`blocks` (`blocked_by`), `unlocks` (`origin`), `informs` (`related`,
weighted), `supersedes`. Derived: `conflicts` from scope overlap among open
tasks. `blocks` and `supersedes` must be acyclic — `scr edge add` refuses a
cycle and logs the attempt. Each edge set has its own hash; `graph_root` folds
them.

## What verify proves

Snapshot matches the tree; the event chain is intact and complete; replaying the
log yields exactly the statuses and edges in the records; invariants hold;
`graph/graph.json` is current. See `docs/hashing.md`.
